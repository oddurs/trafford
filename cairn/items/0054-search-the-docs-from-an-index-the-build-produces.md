## Problem

Documentation is looked *up*, not read through — the same observation that
motivated folding the reading view: a heading every six lines of body means
reference material, and reference material is navigated. Ctrl-F over one page
does not find the answer that is on another one, and adding a hosted search
service means a third party on a page that otherwise makes no outbound requests.

## Proposal

Build the index at build time, search it in the browser.

`vault::Index` already scans, tokenises and searches this exact corpus for the
app's own search. Emit what it knows as a JSON index — page, heading, and a
snippet per section — and ship a small script that queries it.

- The index is a build product, so it cannot fall out of date
- Section-level results, not page-level: a hit lands on the heading, which the
  anchors from #0044 already provide
- Loaded on first keystroke, not on page load; a reader who never searches pays
  nothing
- Degrades to a link to a full index page with JavaScript off

## Acceptance criteria

- [ ] Searching finds sections, and the result links to the heading
- [ ] The index is generated by the build and never committed
- [ ] Nothing is fetched before the first keystroke, and the page still works
      without it
- [ ] The index stays under a size worth stating out loud — a few hundred
      kilobytes, not a few megabytes

## Notes

Filed under `later` deliberately. A site with a dozen pages is searched with
the browser's own find; this earns its place at the point where the docs are
big enough that a reader cannot see the shape of them from the sidebar.

The index format is the decision that matters, because it is the thing the
client script and the generator have to agree on. Whatever it is, generate it
from `vault::Index` rather than re-tokenising the markdown — a second idea of
what a word is diverges the same way a second heading scanner does.
